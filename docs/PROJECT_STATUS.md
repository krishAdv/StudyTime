## What is implemented

- **Stack:** Next.js 16.4.3 (App Router, Turbopack, `cacheComponents` and `partialPrefetching` on), React 19, Tailwind 4, TypeScript. Client-side only: no backend of its own. Supabase is used for sign-in (M3) and, only when cloud sync is turned on (a build flag plus a per-device opt-in, both off by default, M4.3), to sync study data between devices; study data is still saved locally first, per signed-in account on the device (M4.1).
- **Routes** (thin wrappers around `src/features/*`): `/` Dashboard (timer), `/classes`, `/history`, `/insights`, `/settings`, plus `manifest.webmanifest`.
- **Timer:** Stopwatch (default) and Countdown. Start, Pause, Resume, Stop. Paused time is not counted. A countdown that reaches zero saves the full target. Sessions under 1 second are not saved. The mode is locked while a session is active. Only the countdown length is remembered.
- **Classes and subgroups:** create, rename, delete. Subgroups are one level deep. Class names are unique app-wide, subgroup names unique per class (trimmed, spaces collapsed, case-insensitive). The UI disables the button and explains why when a name is a duplicate.
- **Class colors (2026-11-07):** the New class and Edit class dialogs (pencil on a class page) have a 12-color preset picker (`lib/class-colors.ts`, `components/ui/color-picker.tsx`, `features/classes/class-dialog.tsx`); choosing is optional (default: the first preset no class uses yet). The first six presets are the colors classes were given automatically before, in the same order. A non-preset color (e.g. from a backup) shows as a selected "Custom" swatch and is kept unless another is picked. Rename and recolor save atomically through `updateClass` / `updateClassIn` (an unchanged edit saves nothing). The color is shown on the class list, the class page header, subgroup rows, subgroup sessions, History and Dashboard session rows, and Insights bars; colors are accents next to text, never text backgrounds, and the picker's check mark uses black or white by contrast. No data format change and no migration: `color` was already part of the class in localStorage, the export file, the sync snapshot / `add_class` / `update_class` ops and the database (`#rrggbb` check); color conflicts between devices already go through the existing conflict screen.
- **History:** sessions grouped by day, class filter, tap a session to change its class or subgroup (only those two fields change). Subgroup pages show only that subgroup's sessions.
- **Insights:** daily and weekly charts, streaks, per-class totals with a Today / This week / This month / All time dropdown. Local calendar, Monday-start weeks; a session that crosses a boundary is split proportionally.
- **Settings:** light / dark / system theme, and Backup: export study data to a JSON file, or import one (replaces current data after a confirmation).
- **Persistence:** localStorage on this device (see below). PWA manifest and icons exist; there is no service worker.

## Persistence, migrations and reset

- `studytime:data` holds `{version, classes, sessions}`; current version is 2. Version 1 is still read.
- Nested groups from older data are flattened on load (`Parent › Child`), original saved to `studytime:data:pre-flatten-backup`.
- Old sample data is removed once (v1 to v2), original saved to `studytime:data:pre-seed-cleanup-backup`.
- A one-time reset (marker `studytime:reset:2026-10-27`) copied existing data to `studytime:data:pre-reset-backup` and started empty. It does not repeat.
- Unreadable data is kept under `studytime:data:corrupt` and the app starts empty.
- A class with no color, or a color that is not `#rrggbb`, gets a preset on load (`#rgb` is expanded to the same color), so the data stays valid for export and sync. The app has only ever saved `#rrggbb` colors, so real data is unaffected.
- Never delete the `*:pre-*-backup` or `*:corrupt` keys. Theme (`studytime-theme`) and `studytime:countdown-minutes` are separate keys.

**S3 (done): the diff planner, pure.** `src/lib/sync/diff.ts`: `diffToOps(remote, target, options?)` returns the ordered `push_changes` operations that turn the remote snapshot into the target, already cut into batches, or a typed refusal. Still no React, provider integration, network calls, migrations, table writes or new dependencies.
- How the order is guaranteed: the planner simulates the server state and emits an operation only when its preconditions hold there, updating the simulation exactly like the SQL (`delete_group` nulls the subgroup of its sessions; `delete_class` removes its sessions and subgroups; names unique per account for classes and per class for subgroups, under both the app's and a simple lowercasing rule). So the sequence is valid by construction, `expectedSessions` is the simulated count when the delete runs (earlier operations, including those in earlier batches, counted), and a plan whose simulation does not end equal to the target is refused. Sessions move out of a class before it is deleted (a class is never deleted while a session that must survive is in it); a session leaving a subgroup for no subgroup needs no move because `delete_group` does it; classes and subgroups are added in target order, after what they need.
- Names: a wanted name held by another entity is freed by deleting the holder when it can already go, otherwise by renaming the holder to a temporary name (`~sync-N`, chosen to collide with no name in either snapshot under either lowercasing rule). That resolves swaps, rotations of any length and "delete a class and re-create its name", with one temporary rename per cycle.
- Batches: at most 5,000 operations and 3,000,000 UTF-8 bytes of JSON each by default (75% of the server's 4 MB, because the server measures the jsonb value, not the text; both are configurable and capped at the server's limits). Every prefix of a plan is a valid server state, so a cut is valid at any operation boundary, except that a cut is only allowed where the simulated account respects the class (1,000) and session (100,000) caps, which the server checks at the end of every push. The subgroup cap (checked inside a push) is never exceeded at any step. If no allowed cut exists the plan is refused (`no_safe_chunk_boundary`) rather than split unsafely.
- Refused, never approximated: an invalid remote or target snapshot; a session whose start time, duration or mode differs (nothing edits them); a session missing from the target while its class stays (nothing deletes a single session; sessions only leave with their class); unusable options; one operation larger than a batch.
- Limits to keep in mind: existing classes and subgroups cannot be reordered (the server orders by creation), so new ones follow existing ones in target order. A subgroup that keeps its id but changes class is deleted and re-created (its sessions are kept and moved). A multi-batch plan is not atomic: each batch leaves a valid state, but another device could read a half-applied one, so a failed or stale batch must be handled by pulling and planning again.
- Tests added: 71 (`sync-diff` 66, `sync-diff-random` 5; helper `tests/helpers/sync-plan-harness.ts`). Every plan is applied to the in-memory server (every batch accepted, every operation effective, final state equal to the target, a second plan empty). The randomized tests cover 400 seeds, the same seeds with tiny batch limits, and larger snapshots, and also check creation order and refusals. Breaking the planner in seven ways (class deleted too early, no cycle breaking, unsafe cuts, wrong `expectedSessions`, reused subgroup ids, a redundant move, class order) each made tests fail.
- Checks run for S3: `npm test` 31 files, 743 tests pass; `npx tsc --noEmit` and `npx eslint` clean; `npm run build` succeeds.

**S4 (done): the three-way merge, pure, detect-only.** `src/lib/sync/merge.ts`: `merge3(base, local, remote, options?)` returns `merged` (a `target`, plus `resolutions` and `warnings`), `conflicted` (structured `conflicts`, no `target`) or `refused` (an input is invalid, a server cap would be exceeded, the target is ineligible, or S3 cannot plan it; the planner's own error is kept in `error.diff`). Only `merged` has a `target`, so a conflicted result cannot be pushed by mistake. Still no React, provider integration, network calls, migrations or new dependencies; S1 to S3 are unchanged. It takes no resolution input and has no UI.
- Guarantee: valid inputs, no unresolved conflicts and a target that `diffToOps(remote, target)` can plan give `merged` (the planner is run inside `merge3` as the last check). Everything is matched by id, never by name.
- Rules: class fields (`name`, `color`) and group fields (`name`, `classId`) merge one field at a time; one-sided changes are taken, identical changes are taken once (reported as resolutions), different changes to one field conflict. A session's `classId` + `groupId` move as one unit; `startedAt`, `seconds` and `mode` are immutable and any difference between versions of one session refuses the merge (`session_immutable_mismatch`; since S5 Phase 1, previously a conflict). Delete against edit, and delete against an added or modified dependent (a session or subgroup added to or moved into a deleted class, a session moved within it, a subgroup edited in it; a session added or moved into a deleted subgroup) are conflicts. A session moved OUT of a class the other side deleted survives in its new class when that class exists in the result (resolution `moved_session_kept`; the class is still deleted; if the server lost the session with the class, the plan adds it again with the same id and immutable fields); a move to a class that does not survive is still a conflict. An untouched session in a deleted subgroup is ungrouped with a warning, and the other side's move out of a deleted subgroup is kept (a side's own group deletion is not counted as a move). A session missing on a side while its class still exists there conflicts (`session_removal_unsupported`). Name collisions on the merged result (either lowercasing rule) conflict and nothing is renamed. `options.protect` (class and subgroup ids of a running timer) turns a merge that would delete one into a `protected_entity_deleted` conflict; the timer provider is untouched. List order is not merged: the target keeps remote's order, new entities follow sorted by id.
- Tests added in S4: 75 (`sync-merge` 71, now 73 because S5 Phase 1 replaced the two immutable-field tests with four refusal tests; `sync-merge-random` 4; helper `tests/helpers/merge-harness.ts`). Every merged case in the unit tests is planned with S3, applied to the in-memory server and compared with the target. The randomized tests run 300 seeds (valid inputs are never refused; deterministic; swapping the sides gives the same conflicts and data; no session lost and immutable fields unchanged; nothing invented; every merged result converges through the fake server, also in batches of 3; shuffled input order does not change the result; one-sided changes give exactly that side). Frozen inputs prove nothing is mutated. Breaking the merge in five ways (local wins a field conflict, no collision check, no final S3 check, a group deletion counted as a session move, a missing session not a conflict) each made tests fail.
- Checks run at S4 completion: `npm test` 33 files, 818 tests pass (current totals are in the S5 Phase 1 entry below); `npx tsc --noEmit` and `npx eslint` clean; `npm run build` succeeds.
- Limitations: (1) moving a session into a class and then deleting that class, on one device, removes a single session while its original class survives; S3 refuses to plan that, so `merge3` reports `session_removal_unsupported` and that device cannot sync until it is resolved. The existing operations could express it (`move_session` into a class the plan deletes anyway, then `delete_class` with `expectedSessions` counting it, no SQL change), but removal needs explicit authorization, which is deferred to the S5 conflict-resolution design (no `allowSessionRemoval` in S3, no temporary classes). (2) Conflicts carry the three values but nothing resolves them yet. (3) A deletion that conflicts with a modified dependent is reported even when the dependent edit is only a rename. (4) Verified against the in-memory model of the SQL, not the real test project.

**S5 (design approved; Phases 0 and 1 done, Phases 2 and 3 implemented and pending review, Phases 4 and 5 skipped for now): conflict resolution and explicit session removal.** Phase 0 was the documentation cleanup. Phases 1 and 2 are described below. No SQL, migration, UI, storage or engine change was made for S5. Approved design in short; each item says whether it is implemented (Phases 1 and 2 are):
- **Implemented in Phase 1 (applied by `merge3` since Phase 2, for the kinds listed under Phase 2):** one decision point per deleted class or group; versioned (`sf1`) SHA-256 fingerprints over a canonical encoding that distinguishes missing from null; validation that rejects duplicate, stale and malformed decisions without effect; and refusal of immutable session mismatches.
- **Approved, not implemented (Phase 4):** `merge3` will take an optional `revisions: { base, remote }`: a remote older than base will refuse, equal revisions with different data will refuse, and without revisions no automatic remote-origin removal or both-sides-missing acceptance will be allowed (those cases will refuse).
- **Approved, not implemented (Phase 4):** explicit `remove` decisions will be the only way a session can disappear while its class stays. The planner will route the removal as `move_session` into a class the same plan deletes, then `delete_class` with the right `expectedSessions`, in one atomic batch (refused if it cannot fit one batch or no valid routing class exists). Authorization will stay internal to the merge layer. Today `diffToOps` refuses every such removal and `merge3` reports `session_removal_unsupported`.
- **Approved, not implemented (Phase 4):** `merged` will carry the exact validated plan, bound to the remote revision and snapshot digest it was generated against; the future engine will have to verify the binding, push at that revision, and otherwise pull, re-merge and re-plan. Protected (running timer) deletions stay deferred to the engine.
- **Not in S5:** persistent decision storage (only pure serialize/parse and validation), the sync engine, any UI, background synchronization, any SQL migration or new RPC.

**Cross-tab protection (done, pending review).** Tabs of one browser and account share one local storage key but each keeps its own copy of the data in memory, so a tab that missed another tab's change could overwrite it, and a sync pass from it would read the newer data as deleted.
- *How it works:* the account store (`createAccountStore`) remembers the exact stored text this tab last read or wrote. `save` compares the stored text with that first and writes nothing if it differs. A `storage` event, and a re-check when the tab becomes visible, gets focus or is restored from the back/forward cache (Safari suspends background tabs and can deliver no event), notice a change before any save. Once a tab is stale it stays stale until reloaded: it never writes again and never merges.
- *In a stale tab:* every change is refused with a message (add, rename, delete, import, move a session), nothing is saved, and sync is paused: no pass runs, linking and the escape actions are blocked, and a pass that was already running is stopped before it pushes (the engine, first-link upload and Replace cloud each ask `isLocalCurrent()` right before pushing; the data provider answers by re-reading storage). A study session finished in the stale tab is kept in memory so it isn't dropped silently, but is not saved or synced. A banner says "StudyTime was changed in another tab", offers **Reload this tab** and **Download this tab's data**, and never reloads by itself. The Settings sync card shows that sync is paused and disables Sync now.
- *Unchanged:* with one tab nothing differs (no banner, normal saving and syncing). Two tabs that wrote identical text are not in conflict, and if storage can't be read nothing is ever flagged.
- *Tests:* `tests/cross-tab.test.tsx` (22: single tab, another tab writing, detection by event and by visibility, focus and pageshow, detection at save time, refusals, stickiness, recovery by reload, the banner and the download), `tests/cross-tab-sync.test.tsx` (10: a stale tab never pushes and the other tab's new class is not deleted from the cloud, a pass in flight is stopped before it pushes, recovery, first link and Replace cloud are guarded) and `tests/copy-sync-wording.test.tsx` (6: the Import warning and the account-card wording). Seven mutations were each caught (no compare-before-write, not sticky, no visibility re-check, a change allowed when stale, a sync pass allowed when stale, no check before pushing).
- *Remaining risks:* localStorage has no atomic compare-and-swap, so two tabs saving in the same instant can both pass the check and the last write wins (the other tab goes stale at its next check and the banner offers a download). Only the account store is protected; the legacy no-account store (used only when Supabase is not configured) is not. A running timer lives only in memory, so reloading a stale tab loses it (the banner warns that unsaved work is lost, and the download holds the data but not the running timer). The `storage` events and Safari's behavior follow the specification and were tested in jsdom, not in a real Safari; the compare-before-write check does not depend on them. A stale event that arrives after a push has started cannot stop that push, but it was built from data that was current a moment earlier.

*Node:* not pinned. Next 16 needs Node 20.9 or newer, local development uses 24, and `package.json` has no `engines`. A Vercel project keeps the Node version chosen when it is created, so set it to match (24.x) in the project settings at creation. No repository change is needed.
