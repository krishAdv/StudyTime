## Architecture

Next.js App Router (Next 16, React 19, Tailwind 4), client-side only. Study data is local (per signed-in account); Supabase provides sign-in and, only when sync is enabled (build flag `NEXT_PUBLIC_STUDYTIME_SYNC=1` plus a per-device opt-in, both off by default), the sync RPCs (`docs/M4-SYNC-PLAN.md`). Routes in `src/app/*/page.tsx` are thin wrappers around views in `src/features/*`. Path alias `@/*` → `src/*`.

**State is nested providers** (`src/components/providers.tsx`): Theme → Settings → Auth → `AccountBoundary` → (StudyData → Timer, mounted per owner).
- `AccountBoundary` (`features/data/account-boundary.tsx`) picks the data owner: `disabled` (no Supabase env) → legacy bucket `studytime:data`; `loading`/`signed-out` → `SignInWall`, no data provider mounted, nothing read; `signed-in` → bucket `studytime:u:<userId>:data` via `lib/account-store.ts`, keyed by user id so an account change remounts StudyData and Timer (a running timer can never be saved into another account). Account stores do no reset/migrations/backups; sign-out deletes nothing; the legacy bucket and all `*:pre-*-backup`/`*:corrupt` keys are never touched by accounts. `peekLegacyData` reads the legacy bucket read-only.
- `StudyDataProvider` is the single source of truth for `classes` and `sessions`, mirrored to localStorage (`studytime:data`). The account store protects against another tab changing the same account's data (`lib/account-store.ts`: it remembers the stored text this tab last read or wrote, refuses to save over a different one, and tells the provider via `store.watch`); the provider then sets `staleTab`, refuses changes, `DataStatusGate` shows `StaleTabBanner`, and sync pauses (`syncBridge.isStale()`, and the engine's `isLocalCurrent()` before pushing). A stale tab never reloads itself. Every Insights, History and Classes number is derived from `sessions`; never store totals.
- `TimerProvider` persists the active session on this device as soon as it starts, pauses or resumes (`lib/active-session.ts`; key `studytime:u:<userId>:active-session`, or `studytime:active-session` without accounts) and restores it before its first render, so a reload or iOS killing the page loses nothing. Active sessions are local only: never synced, exported or sent to Supabase. On finish the session is first written to the record's `unsaved` list, then `logSession` (which now saves synchronously and returns `saved|dropped|unsaved`), and the record is cleared only when it was saved or dropped; leftovers are re-added on the next start (idempotent by id). Another tab's change to the record is adopted (storage event, visibility, and a re-read before every action). A failed record write is never ignored: `persistWarning` (shown on the timer card) says the session would be lost if the app closes, and the write is retried on every change and when the page is hidden or shown; a restored session whose id is already in study data (its record couldn't be cleared) is not brought back. Timestamps are the source of truth (the 250ms interval just refreshes the UI), and `stateRef` is read synchronously so a double click or tick racing Stop can't save a session twice. Default mode is Stopwatch (`lib/timer-defaults.ts`); mode is not persisted, only the countdown length is.
- `AuthProvider` (`features/auth`) exposes `status` (`disabled|loading|signed-out|signed-in`), `user`, `signIn`, `signOut`. It is UI state only (the database trusts the JWT, never this), and it never touches `studytime:data`. Email + password only, no in-app sign-up (accounts are created in the Supabase dashboard); signed-in users can change their password (`changePassword` re-verifies the current one). Offline with an expired access token, supabase-js returns no session from `getSession()` with an `AuthRetryableFetchError` (public API) and keeps the stored session; the provider then stays signed in as the account last seen signed in on this device (`LAST_USER_KEY` = `studytime:auth:last-user`, written from auth events, removed on `SIGNED_OUT` or when `getSession` reports no session without a network error), so local data and the timer work offline. It never reads supabase-js's own storage key, and a null `INITIAL_SESSION` alone decides nothing. `signOut` uses `scope: "local"` so one device doesn't sign out the others. The client comes from `lib/supabase/client.ts` (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, set in `.env.local` for local runs or in the host's environment settings; there is no `.env.example` file) and is `null` when unset, which means local-only (`status: "disabled"`). Never use the service-role key in this app. supabase-js keeps its session in localStorage under `sb-<project-ref>-auth-token`; leave it alone.
- `AppShell` renders children only after hydration, so providers may read localStorage in their `useState` initializers.

**Domain rules live in pure modules under `src/lib/`, not in components.** Providers route all mutations through them so the rules hold on any code path, and they are written so a database could enforce the same constraints later:
- `class-rules.ts`: name normalization (trim, collapse spaces, case-insensitive), class names unique app-wide, subgroup names unique per class, and subgroups only attach directly to a class. Mutations return `Result<T>` (`{ok, value} | {ok:false, error}`); the UI shows `error` inline (`NameDialog` takes `validate` and an `onSubmit` that may return an error string; classes are created/edited with `features/classes/class-dialog.tsx`, name and color together via `updateClassIn`, atomic).
- `class-colors.ts`: a class color is always `#rrggbb`, the same rule enforced by `data-export.ts`, sync `eligibility.ts` and the database check `classes_color_check`. The first six presets are the old auto-assigned colors, in order; `parseStoredData` repairs missing/invalid colors with `normalizeStoredColor`. Colors are accents only (bars, dots, swatches), never text backgrounds. Class color syncs field by field (`update_class` with `color`; a both-sides change is a `color` conflict in `merge.ts` / `conflict-text.ts`).
- `class-tree.ts`, `session-rules.ts`: one-level group helpers, session reassignment (changes only `classId`/`groupId`) and `sessionsForGroup`.
- `timeframe.ts`: Insights ranges use local calendar, Monday-start weeks. A session is treated as one contiguous block from `startedAt`, so boundary-crossing sessions are split proportionally.
- `lib/sync/*` (M4.3 S1 to S9, all implemented; wired into the app by `features/sync/sync-provider.tsx` behind the build flag and a per-device opt-in, both off by default): `snapshot.ts` / `from-snapshot.ts` convert between the local nested model and the server's flat model (the revision always travels beside the data), `eligibility.ts` reports every server constraint local data would break (structured issues, never repairs), `responses.ts` strictly validates RPC replies, `errors.ts` classifies failures (a stale push is a result, never an error), `api.ts` is the injectable `SyncApi` plus the thin Supabase adapter (RPCs only, never table writes), and `diff.ts` (M4.3 S3) plans the ordered, batched `push_changes` operations from a remote and a target snapshot by simulating the server (it refuses what the RPCs cannot express, such as editing or deleting a single session). `merge.ts` (M4.3 S4) is the pure, detect-only three-way merge `merge3(base, local, remote, options?)` by stable id: `merged` (the only result with a `target`, already checked with `diffToOps`), `conflicted` (structured conflicts, never a partial target) or `refused`; it never drops a session or renames anything (a session moved out of a class the other side deleted keeps its move; net removal of one session stays `session_removal_unsupported`, deferred to S5). `fingerprint.ts` and `decisions.ts` (S5 Phase 1) hold the canonical `sf1:` fingerprints (SHA-256 via the exact-pinned `@noble/hashes`, imported only there) and the decision points/validation; `merge3` returns `decisionPoints` when conflicted and refuses immutable-field mismatches of one session. Since S5 Phase 2 it also takes `options.decisions`: valid, applicable decisions (field/move/add-mismatch keep_local/keep_remote, `rename`, `ungroup`, `ungroup_session`) settle their conflicts, a rename is checked against the final merged names (class names app-wide, subgroup names per final parent class), and rejected decisions are returned in `rejectedDecisions` and change nothing; Phase 3 (restore-only) adds `keep_class` / `keep_group` (the class or subgroup stays, in the version of the side that still has it, with what that side holds); `delete_class` and session removal stay `unavailable`. Phases 4 and 5 were skipped on purpose (see the plan doc). `engine.ts` (S6) is the injected sync engine `createSyncEngine(deps).syncOnce()` (pull, `merge3`, push, backup, then replace local data; baseline saved only after local reached the merged state; never pushes after a conflicted or refused merge); `flag.ts` is the build flag (`NEXT_PUBLIC_STUDYTIME_SYNC=1`, off by default). The engine is used only by `features/sync/sync-provider.tsx` (S7, mounted by `AccountScope` inside `TimerProvider`; needs the flag, a configured backend and a per-device opt-in saved by `lib/sync/device-store.ts`, otherwise nothing runs). Triggers: start, 3 s after a local change, `online`, foreground (throttled); no polling; automatic passes wait while a timer is active. For a linked device, `conflict-text.ts` turns a conflicted pass's decision points into plain-language choices (the Settings card submits them as `syncOnce({decisions})`), and `escape.ts` (S9, `createEscapes(deps)`) holds "use cloud" and "replace cloud": both need a confirmation bound to a fingerprint of what was shown, save safety copies first, and move the baseline only after the state was verified (replace cloud is one atomic delete-and-recreate push built from `diffToOps` in two steps, refused when it doesn't fit). A device with no baseline is linked by `link.ts` (S8; `createLinker(deps)`): `inspect()` only reads, `link(action, seen)` does the one action the user confirmed (upload via `import_and_init_sync`, adopt, use cloud with a backup, or combine through the engine started from an empty baseline), refuses if either side changed since it was shown, and saves the baseline only after the link really happened. `StudyDataProvider.syncBridge` (`getData` / `applyData(expected, next)`) is the only way sync reads or replaces local data. `tests/helpers/fake-sync-server.ts` is an in-memory model of the M4.2 SQL for tests (`tests/helpers/sync-device.ts` simulates a device on top of it). Keep all of it in step with the sync migration.
- `menu-position.ts` + `components/ui/dropdown.tsx`: Insights timeframe dropdown is a portal/fixed-position listbox clamped to the viewport (the old native select could overflow on phones/iPad).

**Provider mutations validate against refs.** `StudyDataProvider` keeps `classesRef`/`sessionsRef` so an action can validate against the latest data and return its result synchronously (two same-name adds in one batch must not both succeed). Keep new mutations on that pattern. `logSession` is idempotent by session id and follows the delete rules: a session for a class deleted mid-timer is dropped, and one for a deleted subgroup is saved on the class with `groupId: null`.

## Data and migrations (localStorage)

- `StudyDataProvider` does not touch localStorage itself: it takes a `store` prop (`StudyDataStore` in `lib/data-store.ts`, default `localStorageStore`) with `load()` (one-time reset, migrations, backups) and `save()`. Both localStorage stores throw from `save()` when the write fails (quota, blocked), so the writer raises `saveError` ("not saved" banner with Retry) instead of failing silently; `load()` never throws. Each may return a value (localStorage: ready on first render) or a Promise (future remote store, which should reject, not throw). The provider exposes `status` (`loading|ready|error`), `retryLoad`, `saveError`, `retrySave`; it never saves before a successful load, refuses mutations until ready, ignores superseded load attempts, and writes snapshots through `lib/serial-writer.ts` (one in flight, newest wins, failed snapshot kept and retried). `DataStatusGate` (in `layout.tsx`, inside `AppShell`) shows the loading/error/save-error UI. Reset/migration/backup logic lives in `createLocalStorageStore`; tests can inject a fake `StorageLike`.
- Backup (Settings → Backup): `lib/data-export.ts` defines the export file (`format: "studytime-export"`, `formatVersion: 1`, `exportedAt`, `data: {classes, sessions}`; documented at the top of the file), strict `validateStudyData`, and `parseExport`. Import goes through `replaceAllData` on the provider (refused until ready, re-validates, replaces atomically, saved through the normal writer); the UI asks for confirmation first and is disabled while a timer runs. Theme and countdown length are never exported or imported.
- Payload `{version, classes, sessions}`; current `DATA_VERSION = 2` (`lib/storage.ts`). `parseStoredData` also accepts v1 and sanitizes input.
- Groups are exactly one level deep. Older nested data is flattened on load (`flattenLegacyGroups`): ids kept so sessions stay valid, nested names become "Parent › Child", original saved to `studytime:data:pre-flatten-backup`.
- `lib/legacy-seed.ts` only recognizes the old sample data for the v1→v2 cleanup (backup: `studytime:data:pre-seed-cleanup-backup`). It is never loaded as data; fresh installs start empty.
- A one-time reset ran via marker `studytime:reset:2026-10-27` (`RESET_MARKER_KEY` in `lib/storage.ts`, applied in `createLocalStorageStore` in `lib/data-store.ts`); it copies the old data to `studytime:data:pre-reset-backup` and must never become recurring.
- Never delete the `*:pre-flatten-backup`, `*:pre-seed-cleanup-backup`, `*:pre-reset-backup` or `*:corrupt` keys. Theme (`studytime-theme`) and `studytime:countdown-minutes` are separate settings keys.
- Tests that seed `studytime:data` must first set `RESET_MARKER_KEY`, otherwise the one-time reset wipes the seed. Account buckets have no reset. Shared test helpers (`tests/helpers/fake-auth.ts`, `memory-storage.ts`) fake Supabase auth with user switching and record storage reads/writes.
- `AccountCard` takes a required `timerActive` prop (Settings passes it) so sign-out is blocked while a timer runs.

## Database (supabase/)

`supabase/migrations/` holds the schema, RLS and `import_local_data` (applied to the user's project; see `supabase/README.md`). The M4.2 migration (`20261029120000_studytime_sync.sql`: `sync_state`, `pull_snapshot`, `push_changes`, `import_and_init_sync`) is applied to a separate Supabase test project only and **not to production** (it passed the SQL suites there, a core API check of 43 checks with isolation and direct-write denial verified, and the Replace cloud Stage A and B checks in `docs/REPLACE-CLOUD-TEST-PLAN.md`; the 1,000-row snapshot case and a real two-connection lock test are untested); it revokes direct client writes to the data tables, so all writes go through definer RPCs. The app reaches these tables only through the three sync RPCs, and only when sync is on. Needs PostgreSQL 15+. Keep the SQL rules in step with `class-rules.ts` / `class-colors.ts` / `data-export.ts` (names normalized, colors `#rrggbb`, group ids unique per user, one level, session group belongs to its class). The only Supabase code in the app is sign-in (`lib/supabase/client.ts`, `features/auth`).

**Never run SQL, `supabase db push` or `supabase db reset --linked` against the linked project** (`supabase/.temp/project-ref` and `.env.local` point at production; both are local and gitignored). The scripts under `scripts/` refuse production and ignore `.env.local` (see `docs/REPLACE-CLOUD-TEST-PLAN.md`). SQL tests (`tests/verify.sql`, then the sync migration, then `tests/sync_verify.sql`) go on a separate test project or local Supabase only; `verify.sql` must run before the sync migration.

## Testing notes

Vitest config is in `vitest.config.ts` (alias `@`, tests in `tests/`). Component/provider tests opt into jsdom with `// @vitest-environment jsdom` and use `@testing-library/react` (call `cleanup()` yourself; globals are off) and fake timers for the timer. Browser checks used `playwright-core` driving the installed Chrome against `next start`.

## Gotchas

- `docs/PROJECT_STATUS.md` records what is verified, known issues and the next milestone; keep it current.
- In `next dev`, every route logs `instant-unrendered-segment` because `AppShell` renders a "Loading…" placeholder instead of `children` until hydration. It is development-only and does not affect the build; do not silence it with `instant = false`. Fixing it properly means removing that gate (a larger refactor, see the status doc).
- `AGENTS.md` says this Next.js version differs from training data; read `node_modules/next/dist/docs/` before using Next APIs.
- UI is mobile-first (iPhone/iPad, light and dark themes): use the CSS variable tokens in `globals.css` (`bg-card`, `text-muted-foreground`, `text-danger`, …), 44px touch targets, and `text-base sm:text-sm` on inputs to avoid iOS zoom.
